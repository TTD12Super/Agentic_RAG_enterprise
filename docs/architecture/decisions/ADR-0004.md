# ADR-0004 — Two-review publication, versioning and maintenance

- Status: Accepted
- Date: 2026-11-09
- Affected: document lifecycle, ingestion workers, queue, chat availability, index and cache

## Context

Documents require administrative review before processing and again before publication. Upload maintenance pauses new chatbot work, while existing approved work must be resumed safely. A failed upload must never replace the former ACTIVE version or permanently lock the chatbot.

## Decision proposal

Use this lifecycle:

UPLOADED → QUARANTINED → REVIEW_1_APPROVED → PROCESSING → PROCESS_VALIDATED → PENDING_REVIEW_2 → ACTIVE. Review 2 approval is a recorded decision required for the transition to ACTIVE, not an additional version status.

Rejected/failed/cancelled versions remain non-searchable. Publication atomically moves the latest approved version to ACTIVE and supersedes the previous version. Affected retrieval/answer caches and derived indexes are invalidated.

An upload starts global maintenance, stops new chat admission and checkpoints or safely quiesces existing jobs. Resumption occurs only at a durable safe boundary or by replaying an idempotent read-only step. External LLM calls are not assumed to pause mid-token.

## Consequences

- The former ACTIVE version remains the safe fallback on rejection or failure.
- Review events, actor identity, policy version, idempotency and cache invalidation are part of the lifecycle contract.
- Queue, checkpoint and maintenance semantics require a separate approved implementation contract.
- The owner-provided baseline proposes that the same administrator may perform both reviews; this remains unapproved until the Project Owner explicitly accepts this ADR.
- Global maintenance creates an intentional availability trade-off and must be measured and visible.

## Approval

Project Owner approved this ADR as the MVP lifecycle baseline on 2026-11-10. Provider-specific pause behavior, retention and permanent-delete safeguards remain subject to their affected policy and operational gates.

## Owner-provided lifecycle parameters

- The same administrator may perform both reviews.
- Retry is limited to three attempts for an unchanged document version; changed content creates a new version.
- Approval expires after 30 minutes. Maintenance has a configurable 60-minute watchdog ceiling and never auto-approves.
- PostgreSQL stores durable checkpoints containing workflow stage, job/version/source IDs, policy version, attempt and timestamps.
- New chat work receives `503 MAINTENANCE_ACTIVE`; existing jobs pause and resume only after authorization and version rechecks.
